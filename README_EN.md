# GrowthBoard Personal Learning and Growth Tracker — Serverless, Runs Entirely on GitHub

![GrowthBoard](./public/og.png)

> Your GitHub is your personal growth database.

A personal growth tracking system backed by GitHub for persistence, while all daily operations are completed directly within the website. Adding, editing, archiving, restoring, and deleting records never redirects you to GitHub, and the page updates immediately after a successful submission. Supports mobile phones, tablets, and other devices.

## Features

- Single repository: source code, configuration, Issues, Actions, and Pages all live in one repository
- GitHub-only: no server, no external database, and no need to keep a local computer running
- Four record types: LeetCode practice, papers, job search, and goals, with a dashboard, statistics, and unified timeline
- Optional modules: LeetCode, papers, job search, and goals can each be enabled or disabled globally; visitors can also hide modules on their current device
- In-site operations: create, edit, archive, restore, and delete records using dialogs inside the website without opening Issue pages
- Immediate feedback: the interface updates immediately after the GitHub API saves successfully and preserves pending records across refreshes until backend deployment finishes
- Responsive: works on desktop, tablet, and 375 px mobile screens, with dark mode support
- Least privilege: requires only a fine-grained token bound to one repository with Issues read and write permission
- Public-only: the current installation and deployment process supports Public repositories only and depends on GitHub Pages for website access

## How It Works

```text
In-site form
    ├─ GitHub REST API → GitHub Issues (backend persistence)
    └─ Update the current page immediately + save pending records
                           ↓
                  GitHub Actions rebuild
                           ↓
                  public/data/*.json
                           ↓
                     GitHub Pages
```

GitHub Issues remain the authoritative cross-device data source, but they no longer serve as the frontend operation interface. After a successful website write, the record is shown immediately. Once the new data generated by Actions is published, the temporary pending state disappears automatically.

### Single-User Editing Protection

Each repository instance allows only that repository's owner account to edit records. When connecting a token, the website verifies both the currently authenticated GitHub account and the repository owner. It also rechecks the identity before creating, updating, archiving, restoring, or deleting records. The data exporter accepts only records created by the repository owner, so even if another account bypasses the website and submits an Issue with a record label, it will not enter the website data.

This rule and the homepage greeting are both derived automatically from the `owner/name` value in `repository`. After another user creates their own repository from the template and updates `repository` in `config/site.json`, the homepage displays that repository owner's account name and only that account can edit records, with no separate display-name or allowlist configuration required.

GitHub Pages is a static website and cannot securely embed repository write credentials. Therefore, every browser that needs write access must configure its own fine-grained personal access token in the website's Settings page. The token is stored only in that browser's `localStorage` when “Remember in this browser” is selected, or in `sessionStorage`; it is never written to the source code, Issues, Actions logs, or build artifacts.

## First-Time Setup

The repository already contains the complete workflows. For first-time use:

1. Open **Actions → Initialize GrowthBoard labels → Run workflow** to create the required labels.
2. Open **Settings → Pages → Build and deployment** and confirm that Source is set to **GitHub Actions**.
3. Open **Actions → Build and deploy GrowthBoard → Run workflow**.
4. Create a GitHub **Fine-grained personal access token**:
   - Under Repository access, select only the current repository.
   - Under Repository permissions, set only **Issues** to **Read and write**.
   - Set a reasonable expiration date and do not grant Contents, Actions, or Administration permission.
5. Open the website's Settings page, paste the token into “Connect background sync,” and verify it.
6. From then on, click the `+` button in the lower-right corner or “Add record” on a module page. You never need to leave the website.
7. Wait for the first deployment to finish, then visit `https://your-username.github.io/repository-name/`.

The default URL for this repository is <https://wei1305.github.io/growth-board/>.

> GitHub automatically grants the token read-only Metadata permission. This is the basic permission required to access the repository API and does not require any additional permission expansion.

## Module Switches

Global switches are located in [`config/site.json`](./config/site.json):

```json
{
  "modules": {
    "leetcode": true,
    "papers": true,
    "jobs": true,
    "goals": true
  }
}
```

After changing a module to `false` and committing the change, that module disappears from the sidebar, mobile navigation, homepage statistics, global search, quick-add menu, and timeline. Data export also skips that module. Set it back to `true` and the next build reads its data from Issues again.

Visitors can also hide modules from the website's Settings page. This preference is stored only in the current browser and does not modify the repository configuration.

## Site Configuration

Continue to edit [`config/site.json`](./config/site.json):

| Field | Purpose |
|---|---|
| `siteName` | Website name |
| `tagline` | Homepage subtitle |
| `repository` | Must use the `owner/repository` format |
| `locale` | Date localization language, for example `zh-CN` |
| `theme` | `light`, `dark`, or `system` |
| `modules` | Global switches for the four modules |
| `profile` | Homepage headline and description |

If you copy the repository, update at least `repository` and `profile`. The homepage greeting automatically uses the repository owner's account name from `repository`.

## Adding and Maintaining Records

The website provides structured forms for four record types:

- LeetCode practice: problem, difficulty, language, algorithm tags, mastery level, and review date
- Papers: paper, venue, research area, reading progress, rating, and summary
- Job search: company alias, position, stage, and next-step date
- Goals: period, target value, current value, due date, and retrospective

Record cards, the job board, goal list, search results, and timeline can all open the in-site editor directly. The editor supports:

- Save changes: update the backend record and refresh the page immediately
- Archive/restore: switch the record state without leaving the website
- Delete: add a backend exclusion marker and hide the record from the website immediately; a second confirmation is required

Issue Forms remain available as compatibility and emergency entry points, but normal use does not require opening them.

> [!WARNING]
> This is a public single-repository setup. Although the website hides the Issue operation interface, backend Issues remain publicly visible. Do not enter phone numbers, private email addresses, identity document numbers, home addresses, salary details, unpublished offers, interviewer evaluations, or confidential company materials in job-search records.

## Automation Workflows

- `build-and-deploy.yml`: reads Issues, runs tests, builds the frontend, and deploys Pages
- `initialize.yml`: initializes type, status, difficulty, and control labels
- `validate.yml`: runs type checks, Python tests, and production builds in Pull Requests

The data exporter automatically paginates through all Issues, excludes Pull Requests, tolerates empty optional fields, and writes invalid records to `invalid-records.json`, preventing one malformed record from blocking the entire website.

## Local Development

Requires Node.js 22.13+ and Python 3.11+:

```bash
npm ci
npm run dev
```

Common checks:

```bash
npm test
npm run build
```

Local development uses the demo data in `public/data/` by default. To generate data from GitHub Issues:

```bash
GITHUB_REPOSITORY=owner/repository GITHUB_TOKEN=your_token python scripts/export_data.py
```

Never write the token into source code, `VITE_*` environment variables, Issues, or commits. The token configured in the website is stored only in the current browser. On a public computer, clear “Remember in this browser” and click “Disconnect” when finished.

The page's Content Security Policy permits connections only to its own resources and `api.github.com`, and it loads no third-party scripts. Continue to use repository-scoped, least-privilege tokens with expiration dates.

## Acceptance Scope

- No horizontal page scrolling at 375 px width
- Light/dark themes, search, filtering, mobile navigation, and module switches work
- Creating, editing, archiving, restoring, and deleting records in the website never redirects to GitHub
- The current page updates immediately after a successful API save, and pending records remain visible across refreshes
- Issue changes still trigger automatic data export and Pages deployment
- Invalid Issues do not affect other records
- Build artifacts do not contain the token
- Supports at least 1,000 records through GitHub API pagination with 100 records per page
